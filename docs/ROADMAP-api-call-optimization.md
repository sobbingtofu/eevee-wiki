작성일: 2026-07-26 (2026-08-02 2차 개정 — Phase 1을 무한스크롤 페이지네이션으로 재정의)
선행 작업: 기술 학습 정보 세대 → 버전 단위 전환 (Phase 0~6 완료)

## 0. 배경

버전 단위 전환을 마친 뒤 응답 지연을 손봤다. 가장 컸던 것은 인덱스였다 —
`TB_CXN_POKEMON_MOVES`(54만 행)의 PK 선두 컬럼이 `pokemonId`인데 검색은 `moveId`부터 걸어
인덱스를 탐색하지 못하고 전 구간을 훑고 있었다. 커버링 인덱스로 **1497ms → 4.6ms**.

그 과정에서 한 번 잘못된 판단을 했다. 기술 상세를 검색 응답에 얹어 왕복을 없앴는데,
그건 **검색(후보 N건)과 상세(고른 1건)라는 서로 다른 계약을 섞은 것**이었다.
되돌리고 "가리켰을 때 prefetch"로 바꿨다.

이 로드맵은 그 실수를 겪고 나서 **같은 성격의 문제가 더 있는지 전수 검수한 결과**다.

### 판단 기준

작업 중 트레이드오프가 생기면 아래 순으로 따진다.

1. **계약이 섞이는가** — 성능 이득이 있어도 서로 다른 목적의 API/타입을 묶지 않는다
2. **비용과 이득의 발생 빈도가 같은가** — "모든 요청이 내는 비용"으로 "가끔의 이득"을 사지 않는다
3. **이미 있는 완충 장치를 세는가** — 미리보기·캐시로 가려진 지연은 실제 체감보다 작다
4. **개선 효과를 실측했는가** — 재보지 않은 이득을 근거로 쓰지 않는다
5. 그다음에 숫자를 본다

> 4번은 이번 검토에서 추가됐다. 초판 Phase 2에서 측정하지 않은 렌더 개선을
> 기정사실처럼 적었고, 그 지적을 받아 등급을 내렸다. 아래 Phase 2 참조.

## Phase 1 — 무한스크롤 페이지네이션

### 결정 배경

초판은 "정렬을 클라이언트로 옮기자"였다. **철회했다.**

정렬은 데이터 집합을 소유한 쪽, 즉 서버의 일이다. 그리고 초판 스스로
"페이지네이션을 넣으면 정렬은 반드시 서버로 돌아와야 한다"고 적었으니,
지금 옮기는 것은 나중에 원위치시킬 작업이었다.

**서버 정렬을 유지한 채, 재전송량 자체를 줄이는 쪽으로 방향을 바꾼다.**
초판이 지적한 문제(정렬 변경 시 241KB 재전송, 정렬 조건별 캐시 8벌)는
페이지네이션으로 한 페이지치만 오가게 되면 대부분 해소된다.

### 사양

| 항목            | 값                                                          |
| --------------- | ----------------------------------------------------------- |
| `pageSize`      | **24** (한 행에 2·3·4개 → 세 경우 모두 딱 떨어지는 공배수)  |
| 방식            | offset 기반 (`page` 번호)                                   |
| 트리거          | 목록 마지막 아래의 **보이지 않는 감지용 div**가 뷰포트 진입 |
| 로딩 표시       | 목록 하단에 **"데이터를 가져오는 중입니다"**                |
| 정렬            | 서버 (변경 없음)                                            |

### 서버: 어디서 잘라야 하는가 (핵심)

여기가 이 작업에서 가장 주의할 지점이다.

**현재 정렬은 DB가 아니라 JS에서, 응답을 전부 조립한 뒤에 수행된다**
(`route.ts` Step 6, `sortLearningPokemons`). 정렬 기준이 `koreanName`(ko 로케일 정렬)과
`stats` JSONB 합산이라 PostgREST의 `.order()`로는 표현할 수 없기 때문이다.

그래서 **"DB에서 24행만 읽어오기"는 지금 구조로는 불가능하다.**
전체 순서를 알아야 24개를 고를 수 있고, 순서를 알려면 자격을 만족한 전원의
이름과 스탯이 필요하다.

다만 **자르는 위치를 잘 고르면 무거운 조회는 24마리치로 줄일 수 있다.**
현재 Step 3~5를 살펴보면 세 조회의 무게가 크게 다르다.

| 조회                             | 무게   | 정렬에 필요한가 |
| -------------------------------- | ------ | --------------- |
| Step 3 `TB_POKEMONS` (이름·스탯) | 중간   | **필요**        |
| Step 4 타입 맵                   | 가벼움 | 불필요          |
| Step 5 `fetchLearnInfoMap`       | **무거움** (241KB의 주범) | 불필요 |

따라서 순서를 이렇게 바꾼다.

```
Step 1~2  교집합 계산                    → 전원 (변경 없음, pokemonId만 읽어 가볍다)
Step 3    TB_POKEMONS 이름·스탯 조회      → 전원 (정렬에 필요)
Step 3.5  ★ 정렬                          → 전원
Step 3.6  ★ slice(page*24, +24)           → 여기서 24마리로 좁힌다
Step 4~5  타입 맵 + 학습정보 조회         → 24마리치만  ← 절감이 발생하는 지점
Step 6    응답 조립
```

기존 Step 3~5는 `Promise.all`로 묶여 있는데, **이 변경으로 Step 3이 앞으로 빠지고
Step 4~5만 병렬로 남는다.** 왕복이 2라운드 → 3라운드로 한 번 늘지만,
전송량이 1/18로 줄어드는 쪽이 압도적으로 크다.

> **나중에 더 줄이려면**: Step 3까지 24행으로 줄이려면 정렬을 Postgres로 내려야 하고,
> 그러려면 스탯 합계를 생성 컬럼(generated column) + 인덱스로 만들어야 한다.
> Step 3이 병목으로 측정될 때 검토한다. 지금은 아니다.

### 서버: 응답 형태 변경

총 건수를 헤더에 표시해야 하므로(`배우는 포켓몬 432`) 배열만으로는 부족하다.

```ts
// 이전
type SearchLearningPokemonsResponse = LearningPokemonItem[];

// 이후
interface SearchLearningPokemonsResponse {
  items: LearningPokemonItem[];
  totalCount: number; // 자격을 만족하는 전체 마릿수 (페이지와 무관)
  page: number;
  hasNextPage: boolean;
}
```

요청에는 `page: number`(0부터)가 추가된다.

> **"계약을 섞는 것 아닌가"에 대해**: 아니다. `totalCount`·`page`·`hasNextPage`는
> **같은 자원에 대한 페이지네이션 메타데이터**이지, 다른 자원의 데이터가 아니다.
> Phase 0~6에서 되돌렸던 것(검색 API가 상세 정보까지 싣던 것)과는 성격이 다르다.

### 클라이언트: 조회 계층

`useSearchLearningPokemonsQuery` → **`useInfiniteQuery`로 교체**한다.

- `queryKey`에서 `page`는 **빼야 한다.** 페이지는 `pageParam`으로 관리되며,
  같은 검색 조건의 모든 페이지가 하나의 캐시 엔트리에 누적된다
- `getNextPageParam: (last) => (last.hasNextPage ? last.page + 1 : undefined)`
- `sortKey`·`sortDirection`·`versionName`·`learnMethods`·`moveIds`는 queryKey에 그대로 유지
  → 조건이 바뀌면 **자동으로 1페이지부터 다시 시작**한다 (별도 리셋 코드 불필요)
- 화면에 넘길 목록: `data.pages.flatMap((p) => p.items)`

### 클라이언트: 감지 요소

```
<div className="grid ...">…24×N개 카드…</div>
<div ref={sentinelRef} className="h-px" aria-hidden />   ← 보이지 않는 감지 요소
{isFetchingNextPage && <p>데이터를 가져오는 중입니다</p>}
```

`IntersectionObserver`로 감지한다. 주의할 점 세 가지:

1. **`root`는 기본값(뷰포트)으로 둔다.** 결과 영역이 데스크톱에서는 `overflow-y-auto` 패널,
   모바일에서는 바텀시트라 스크롤 컨테이너가 다른데, 뷰포트 기준 교차 판정은 양쪽 모두
   올바르게 동작한다. `root`를 컨테이너로 지정하면 두 경우를 나눠 처리해야 한다
2. **`rootMargin: "200px"`** 정도를 줘서 바닥에 닿기 전에 미리 요청한다
3. **`hasNextPage && !isFetchingNextPage`일 때만 호출한다.**
   마지막 페이지에서는 감지 요소가 계속 보이는 상태로 남으므로 이 가드가 없으면 무한 반복된다

### 클라이언트: 기존 오버레이 로더 처리 (놓치기 쉬움)

`LearningPokemonsSection`은 지금 `isFetching`일 때 결과 영역 전체를 반투명 오버레이로 덮는다.
`useInfiniteQuery`에서는 **다음 페이지를 불러올 때도 `isFetching`이 true가 되므로,
스크롤할 때마다 목록 전체가 덮인다.**

→ 오버레이 조건을 **`isFetching && !isFetchingNextPage`** 로 바꾼다.
   (검색 실행·정렬 변경·필터 변경 = 전체 오버레이 / 다음 페이지 = 하단 문구)

### 결과 (실측 완료, 2026-08-02)

|                        | 이전              | 이후                   |
| ---------------------- | ----------------- | ---------------------- |
| 최초 응답 크기 (432건) | 241KB             | **13.6KB** (−94%)      |
| 최초 응답 시간         | 440ms             | **248ms** (중앙값)     |
| 정렬 변경 시 전송량    | 241KB             | **13.6KB**             |
| 정렬 조건별 캐시       | 8벌 × 전체 데이터 | 8벌 × 본 페이지까지만  |
| DB 왕복                | 2라운드           | 3라운드 (전송량과 교환) |

**응답 시간 개선폭은 크기 개선폭에 못 미친다.** 전송량이 1/18이 됐는데 시간은 절반 남짓이다.
남은 시간은 전송이 아니라 **Step 1~3**(교집합 계산 + 자격 포켓몬 전원의 이름·스탯 조회)에 있고,
이 부분은 페이지네이션과 무관하게 전량을 봐야 하므로 줄지 않았다.
왕복이 한 라운드 늘어난 것도 일부 상쇄했다.

> 여기서 더 줄이려면 정렬을 Postgres로 내려 Step 3까지 24행으로 만들어야 한다.
> "하지 않기로 한 것" 참조 — 지금 착수할 근거는 없다.

### 측정했으나 손대지 않은 것

정렬 방식별 응답 시간에 차이가 있는지 확인했다. `localeCompare(a, b, "ko")`를
비교마다 호출하는 것이 느릴 것으로 의심해 `Intl.Collator` 재사용과 비교했는데,
**432건 정렬 기준 차이가 1.2ms**였다. 응답 시간 차이(name 248ms / hp 251ms)는
전부 네트워크 노이즈였다. 근거가 없으므로 고치지 않았다.

### 전제 (다르면 알려주실 것)

- 헤더의 `배우는 포켓몬 432`는 **로드된 개수가 아니라 전체 마릿수**를 계속 표시한다
- 정렬·필터·버전을 바꾸면 **목록이 1페이지로 리셋**되고 스크롤도 맨 위로 간다
- "더 보기" 버튼은 두지 않는다 (요청하신 감지 요소 방식만)

## Phase 2 — 기술명 조회를 부모로 끌어올림 (구조 정리)

### 등급 조정

초판은 이것을 성능 개선으로 분류했다. **잘못된 분류다.**

- **네트워크 이득: 정확히 0.** React Query가 같은 queryKey를 합쳐 요청은 원래 1건이고,
  그나마도 기술 바구니에서 이미 prefetch해 둔 값이라 **요청이 아예 나가지 않는다.**
- **렌더 이득: 미측정.** 초판은 검증 항목에 "스크롤이 이전보다 부드러운지"를 넣었는데,
  버벅인다는 증거를 확보하지 않은 채 개선 효과를 전제한 것이었다.
  실제로는 이미지 432장 + 카드 432개 렌더가 압도적으로 무겁고,
  구독 1296개의 마운트 비용은 그 일부에 불과할 가능성이 높다.

따라서 **성능 항목에서 내리고, 구조 정리 항목으로 남긴다. 우선순위는 최저.**
미뤄도 아무것도 깨지지 않는다.

### 그럼에도 수행하는 이유 (하나뿐)

**리프 컴포넌트가 부모가 이미 아는 값을 전역 캐시에서 직접 꺼내 쓰고 있다.**

```
LearningPokemonsSection  ← committedMoveIds를 안다
  └ LearningPokemonCard (×432)
      └ MoveLearningMethodsArea (×기술수)
          └ useMoveKoreanName(moveId) → useQuery  ← 여기서 전역 캐시로 직행
```

기술 이름은 사용자가 바구니에 담는 순간 클라이언트가 이미 가진 값이다.
알고 있는 것을 리프에서 1296번 다시 조회하고 있다.
데이터를 위에서 아래로 흐르게 만드는 것, 그 하나가 근거다.

### 복잡도 검토 (우려에 대한 확인 결과)

"prop을 한 단계 더 내려야 한다"는 초판 서술은 부정확했다. 실제 코드는 이렇다.

- `LearningPokemonCard`는 **이미 `moveIds: number[]`를 prop으로 받고 있다**
- `MoveLearningMethodsArea`는 **`LearningPokemonCard.tsx` 같은 파일 안의 하위 함수**다

그러므로 이 작업은 prop 추가가 아니라 **`moveIds: number[]` → `moveNames: Map<number, string>`
교체**다. `Map`은 삽입 순서를 보존하므로 지금 `moveIds`가 갖고 있던 순서 정보도 그대로 살아 있다.

| 항목                             | 현재                    | 적용 후          |
| -------------------------------- | ----------------------- | ---------------- |
| `LearningPokemonCard`의 prop 수  | 2개                     | 2개 (동일)       |
| `hooks/useMoveKoreanName.ts`     | 존재                    | **삭제**         |

## Phase 3 — `moves/[id]/learning-pokemons` 병렬화

### 요약

**초판은 대상이 3곳이라고 했으나, 실제 대상은 1곳이다.**
나머지 두 곳은 병렬화가 원리적으로 불가능하다. 아래에 이유를 풀어 둔다.

### 왜 3곳 → 1곳인가

초판을 쓸 때 세 라우트를 "다 같은 문제"로 묶었는데, 코드를 다시 읽어 보니 그렇지 않았다.
병렬화가 가능하려면 **두 조회가 서로의 결과를 필요로 하지 않아야** 한다.
그 기준으로 하나씩 보면:

**`pokemons/[id]/moves` — 병렬화 불가**

```
학습 데이터 조회 → 거기서 moveId 목록을 뽑아 → 기술 상세 조회 → 거기서 typeId를 뽑아 → 타입 조회
```

각 단계가 **바로 앞 단계의 결과를 입력으로 받는다.** 앞 조회가 끝나기 전에는
다음 조회에 무엇을 넣어야 할지 알 수조차 없다. 동시에 보낼 방법이 없다.

**`pokemons/[id]/evol` — 병렬화 불가**

```
자기 행 조회 → chainId를 얻어 → 같은 체인의 포켓몬들 조회 → 그 id들로 → 타입 조회
```

같은 이유다. 완전한 사슬이다.

**`moves/[id]/learning-pokemons` — 병렬화 가능 ✅**

```
학습 데이터 조회 → pokemonId 목록 확보
                    ├── 포켓몬 기본 정보 조회  ┐ 둘 다 pokemonIds만 필요
                    └── 타입 맵 조회           ┘ 서로를 필요로 하지 않음
```

마지막 두 조회는 **둘 다 `pokemonIds`에만 의존**하는데 지금은 하나가 끝나기를 기다렸다가
다음을 보내고 있다. 여기만 `Promise.all`로 묶을 수 있다.

덧붙여, 앞의 두 라우트는 `TB_TYPES` 프로세스 캐시가 붙은 뒤로 마지막 타입 조회 왕복이
이미 사라진 상태다. 실제 DB 왕복은 각각 2~3회뿐이라 병렬화 여지가 있어도 이득이 작았을 것이다.

### 작업 내용

`app/api/moves/[id]/learning-pokemons/route.ts` 한 곳.
`search-learning-pokemons`에 이미 적용한 것과 동일한 패턴이다.

```ts
const [pokemonResult, typesMap] = await Promise.all([
  supabaseServer.from("TB_POKEMONS").select(...).in("pokemonId", pokemonIds)...,
  fetchPokemonTypesMap(pokemonIds),
]);
```

### 결과 (완료, 2026-08-02)

왕복 3라운드 → 2라운드.

|             | 이전  | 이후            |
| ----------- | ----- | --------------- |
| 응답 시간   | 357ms | **215ms** (중앙값) |
| 응답 크기   | 115KB | 115KB (동일)    |

`curl` 검증: 432건, 타입 누락 0건, 학습방법 누락 0건,

### 참고

**이 라우트는 아직 어느 화면에서도 호출되지 않는다** (기술 상세 페이지 미구현).
따라서 브라우저에서 체감할 것이 없고, 사용자 확인 항목도 발생하지 않는다.

## Phase 4 — `Cache-Control` 헤더

### 문제

**전체 API에 `Cache-Control`이 하나도 없다.** Next.js Route Handler는 기본이 no-store다.

특히 `/api/versions`는 PokeAPI 동기화 때만 바뀌는데도 새로고침마다 왕복한다.
서버에 5분 TTL 캐시가, 클라이언트에 `staleTime: Infinity`가 있지만
**둘 다 첫 요청은 막지 못한다.** 브라우저 캐시만이 그걸 막는다.

### 전제 (확정)

이 프로젝트의 API는 **전부 인증 없는 공개 데이터**이며, **모든 사용자에게 동일한 응답을
반환한다.** 사용자별로 달라지는 응답이 없으므로 `public` 지시자를 안전하게 쓸 수 있다.

### 작업

| 라우트                                     | 제안                                               | 근거                              |
| ------------------------------------------ | -------------------------------------------------- | --------------------------------- |
| `/api/versions`                            | `public, max-age=300, stale-while-revalidate=3600` | 서버 TTL과 동일하게 맞춤          |
| `/api/moves/[id]/brief`·`detail`           | `public, max-age=3600`                             | 동기화 전까지 불변                |
| `/api/pokemons/[id]`·`evol`                | `public, max-age=3600`                             | 〃                                |
| `/api/moves/[id]/learning-pokemons`        | `public, max-age=600`                              | 〃 (버전별 결과)                  |
| `/api/moves/search`·`/api/pokemons/search` | `public, max-age=60`                               | 타이핑 중 같은 검색어 재조회 흡수 |
| `POST /api/search-learning-pokemons`       | **없음**                                           | POST는 브라우저 캐시 대상이 아님  |

작고 되돌리기 쉬우며 코드 구조를 건드리지 않는다.

## 검증 계획

### 자동 (작업자)

- `npx tsc --noEmit` / `npx eslint .` / `npm run build`
- **회귀 지표**: 스칼렛·바이올렛 + 파괴광선 → **432마리**, champions + 파괴광선 → **205마리**

  - `page: 0`이 24건 + `hasNextPage: true`
  - 마지막 페이지(432 ÷ 24 = 18페이지, 즉 `page: 17`)가 24건 + `hasNextPage: false`
  - **전 페이지를 이어붙이면 432건이고 중복·누락이 없는지** ← 가장 중요
  - 정렬 기준·방향별로 첫 페이지 첫 항목이 기존 응답의 첫 항목과 같은지

**Phase 1**

## 하지 않기로 한 것

- **정렬의 클라이언트 이동** — 철회. 서버 정렬 유지 (Phase 1 참조).
- **정렬을 Postgres로 내리기** — 스탯 합계 생성 컬럼 + 인덱스가 필요하다.
  Phase 1 이후 Step 3(전원 이름·스탯 조회)이 병목으로 **측정되면** 검토한다.
- **검색 `ilike '%q%'`의 인덱스 부재** — 앞 와일드카드라 인덱스를 못 쓰지만
  `TB_MOVES` 937행 / `TB_POKEMONS` 1077행이라 seq scan이 16ms다.
  데이터가 10배가 되면 `pg_trgm` GIN 인덱스를 검토한다. 지금은 아니다.
- **`MoveBucketPreview` 제거** — prefetch가 붙어 대부분 캐시 적중이라 거의 안 타지만,
  **호버 없이 바로 클릭하는 경로에서는 여전히 유효**하다. 남긴다.
- **`search-learning-pokemons` RPC 통합** — Postgres 함수로 묶으면 1왕복이 되지만
  구조를 크게 건드려야 한다. Phase 1로 전송량이 1/18이 되면 남는 비용이 작아지므로,
  **Phase 1 재측정 결과를 보고** 필요 여부를 다시 판단한다.
